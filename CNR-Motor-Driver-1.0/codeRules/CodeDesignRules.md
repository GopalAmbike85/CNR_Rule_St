# Code Design Rules (CNR Motor Driver Firmware)

Version: v1
Date: 02-08-2026

## Purpose

Architecture rules for a project built almost entirely on ST's Motor Control
SDK (MCSDK) plus STM32CubeMX-generated glue, with one fully custom module.
The goal is protecting the boundary between vendor/generated code and the
small amount of code this project actually owns.

> **Related:** naming/style rules are in [CodeQualityRules.md](CodeQualityRules.md).
> Scope table and the vendor-detection grep are defined there — reuse it, don't
> duplicate a second file list here.

---

## Rule 1 — Vendor Files Are Immutable

### 1.1 Requirement

Any file whose header contains `Motor Control SDK Team, ST Microelectronics`
must never be hand-edited. This is ST's own SDK code (FOC control loop, PWM
drivers, comms protocol stack, register access) — 47 of 58 source files as of
02-08-2026.

### 1.2 Why

1. ST periodically updates MCSDK; hand edits get silently lost or conflict on
   the next SDK upgrade.
2. These files are the safety-critical control loop (current/speed limits,
   fault handling) — modifying them outside ST's own review process is a
   physical-safety risk, not just a maintainability one.

### 1.3 Detection procedure

```bash
# Confirm a file is vendor before ever proposing an edit to it
grep -q "Motor Control SDK Team" <file> && echo "VENDOR — do not edit"

# In CI/PR review: diff changed files against the vendor list
git diff --name-only origin/main... -- Src Inc | while read -r f; do
  grep -q "Motor Control SDK Team" "$f" 2>/dev/null && echo "BLOCKING: vendor file modified: $f"
done
```

Any PR touching a vendor file is a **blocking** finding unless the change is
confined to a `USER CODE BEGIN/END` block (see Rule 3) — check which applies
before flagging, since some vendor-authored files (`mc_tasks.c`,
`mc_config.c`, etc.) also contain CubeMX `USER CODE` markers.

### 1.4 Resolution pattern

Don't edit the vendor file. Instead:
- If ST provides a `__weak` hook for this behavior, override it in
  project-owned code (Rule 2).
- If no hook exists, this is a real gap — raise it for discussion rather than
  patching ST's source directly.

## Rule 2 — Weak-Hook Overrides Must Match Vendor Signature and Explain Why

### 2.1 Requirement

When project code overrides an ST `__weak` function, the override must:
1. Keep the exact vendor function name and signature (no renaming).
2. Carry a comment explaining *why* the override deviates from MCSDK
   default behavior.

### 2.2 Reference example already in this codebase

`Src/main.c`'s file header documents overriding `R3_1_SwitchOnPWM` /
`SwitchOffPWM` / `TurnOnLowSides` to keep DRV8316 `nSLEEP` always high,
because MCSDK's default `ES_GPIO` mode toggles that pin on every
`SwitchOn`/`SwitchOff` and puts the current-sense amplifiers to sleep. This
rule simply codifies that existing, already-good practice so future
overrides follow the same discipline.

### 2.3 Detection procedure

```bash
grep -rn "__weak" Src/ Inc/ | grep -v "Motor Control SDK Team"
```
For each match, confirm a comment within ~10 lines explains the deviation
from default MCSDK behavior. No comment = flag for the PR author to add one.

### 2.4 XML category

`category="WeakHookOverride"`

## Rule 3 — CubeMX-Generated Files: Hand Code Only Inside `USER CODE` Markers

### 3.1 Requirement

`main.c`, `main.h`, `stm32g4xx_it.c/.h`, `stm32g4xx_hal_msp.c`, and the other
files carrying `/* USER CODE BEGIN ... */` / `/* USER CODE END ... */`
markers are regenerated by STM32CubeMX/CubeIDE whenever peripheral
configuration changes. Hand-written logic must live only inside those
marker blocks. Code placed outside them is silently deleted on the next
regeneration.

### 3.2 Detection procedure

1. `grep -n "USER CODE BEGIN\|USER CODE END" <file>` to find the marker
   pairs.
2. For a PR's diff on one of these files, confirm every added/changed line
   falls between a `BEGIN`/`END` pair.
3. A change outside any marker pair is a **blocking** finding — it will not
   survive the next CubeMX regeneration.

### 3.3 XML category

`category="CubeMXUserCodeBoundary"`

## Rule 4 — `motor_telemetry_math.c/h` Must Stay MCSDK/HAL-Independent

### 4.1 Requirement

`Src/motor_telemetry_math.c` and `Inc/motor_telemetry_math.h` must not
`#include` any MCSDK or STM32 HAL header. This is explicit in the file's own
header comment ("Compiled/tested on a host build (no STM32 HAL / MCSDK
headers required, no hardware access)") and is exactly what makes this
module unit-testable with Unity on the CI host runner (see
`unit_tests/` and `code_qulity.yml`'s coverage job). An added include would
silently break host-buildability without necessarily breaking the ARM build,
so this needs an explicit check rather than relying on the ARM build to
catch it.

### 4.2 Detection procedure

```bash
grep -n "^#include" Src/motor_telemetry_math.c Inc/motor_telemetry_math.h
```
Any include other than `<stdint.h>`, `<stdbool.h>`, `<math.h>`, or the
module's own paired header is a **blocking** finding.

### 4.3 XML category

`category="HostTestabilityBoundary"`

---

## Rule 5 — Duplicated Math Between `main.c` and `motor_telemetry_math.c` Must Stay in Sync

### 5.1 Requirement

`motor_telemetry_math.c`'s header states it is "a standalone duplicate of
the same formulas" as inline telemetry math in `main.c`, "kept in sync by
hand," and warns that if the inline math in `main.c` changes without a
matching update, the unit tests will "silently verify stale logic."

This is a genuine, already-documented risk — not a hypothetical one. Treat
any PR that touches telemetry/diagnostics math in either file as needing a
design-review check of the other file, since nothing in CI currently
compares them automatically.

### 5.2 Detection procedure

There is no reliable automated equivalence check across a host-only file and
MCSDK-dependent inline code (different types, different scaling context) —
this rule is a **PR-review prompt, not a static check**:

> "This PR changes telemetry/diagnostic math in `main.c` / `motor_telemetry_math.c`.
> Confirm the other file's formulas still match, or explain why they now
> intentionally diverge."

### 5.3 XML category

`category="TelemetryMathDrift"` (reported as a review prompt, not an
auto-detected error — see report format note in the Execution Loop).

## Execution Loop

1. Recompute the vendor/custom/CubeMX-generated file split
   ([CodeQualityRules.md](CodeQualityRules.md) Scope section).
2. Rule 1 — check any file in a PR's diff against the vendor list.
3. Rule 2 — grep for `__weak` overrides in non-vendor code; verify each has
   an explanatory comment.
4. Rule 3 — for CubeMX-generated files in the diff, confirm changes are
   confined to `USER CODE` marker blocks.
5. Rule 4 — confirm `motor_telemetry_math.c/h` includes stay HAL/MCSDK-free.
6. Rule 5 — if the diff touches telemetry math in either `main.c` or
   `motor_telemetry_math.c`, emit a review prompt (not an error).
7. Write `codeRules/reports/CodeDesignReport.md` (or merge into the shared
   `CodeQualityReport.md` — see report format above).
